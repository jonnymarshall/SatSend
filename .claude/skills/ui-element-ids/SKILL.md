# UI Element IDs

Whenever you edit a frontend file (TSX, JSX, HTML, or component) as part of UI or feature work, apply hierarchical IDs to meaningful elements. This lets the user refer to elements by ID in conversation rather than describing them verbally.

**Do not apply this skill during bug fixes**, even if the fix touches a frontend file. Apply it when the task is primarily UI or feature work.

## What gets an ID

Apply IDs to:
- Form controls: `<input>`, `<select>`, `<textarea>`, `<checkbox>`, `<radio>`
- Interactive elements: `<button>`, significant `<a>` tags
- Labels: `<label>` elements paired with controls
- Semantic containers: `<form>`, `<section>`, `<article>`, `<nav>`, `<header>`, `<footer>`, `<main>`, `<dialog>`, `<aside>`
- Logical grouping divs: a `<div>` or `<div>`-like wrapper that contains a related cluster of elements (e.g., a field group, a card, a panel, a toolbar)
- Headings: `<h1>` through `<h6>`
- Tables and significant list containers

Do **not** apply IDs to:
- Pure layout/spacing wrappers with no semantic meaning (e.g., a `<div className="flex gap-2">` that only handles positioning)
- Decorative or icon-only elements
- Utility wrappers generated by UI libraries (e.g., Radix primitives you don't author)

When in doubt about a borderline element, give it an ID.

## Naming format

Use kebab-case with `--` as the hierarchy separator:

```
{page-or-feature}--{component}--{element}
```

Examples:
- `id="invoice-form--client-section--name-input"`
- `id="invoice-form--client-section--name-label"`
- `id="invoice-form--line-items--add-button"`
- `id="invoice-form--line-items"` (container for repeated items)
- `id="dashboard--invoice-table--header"`
- `id="settings--profile-card--email-input"`
- `id="nav--main-menu"`

Rules:
- No two elements may ever share an ID (IDs are globally unique per page)
- Use the component or section name at the top level, not generic names like `container` or `wrapper`
- Be specific: `client-name-input` not `input-1`
- For root-level page sections, one level is fine: `id="invoice-form"`, `id="dashboard-header"`

## Repeated/dynamic elements (proxy-id)

For elements rendered in a loop (e.g., `.map()`), duplicate IDs would break HTML rules. Instead of an `id`, add a `proxy-id` class using the same naming convention. This class exists solely to identify element types in conversation — it must never be targeted by CSS or used for styling.

```tsx
// List container gets a real ID
<ul id="invoice-form--line-items">
  {items.map((item) => (
    // Each item gets a proxy-id class for identification only
    <li key={item.id} className="proxy-id--invoice-form--line-items--item">
      <input className="proxy-id--invoice-form--line-items--description-input" ... />
      <button className="proxy-id--invoice-form--line-items--delete-button" ... />
    </li>
  ))}
</ul>
```

The `proxy-id--` prefix makes these instantly recognisable as identification-only classes. Never style them.

## When you edit a file

1. Apply IDs (or proxy-id classes for repeated elements) to every new element you add.
2. Sweep the rest of the same file for existing elements that lack IDs and should have them, and add those too. This keeps coverage trending upward over time.
3. Do not rename or alter existing IDs unless they are clearly wrong or duplicated.

## Full sweeps

Only run a full sweep of existing files or the entire frontend if the user explicitly asks. Apply IDs and proxy-id classes systematically to every file using the actual component/page names to build the hierarchy.
