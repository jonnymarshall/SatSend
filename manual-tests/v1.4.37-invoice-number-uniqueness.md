# v1.4.37 — Invoice-number uniqueness (roadmap v1.4.23.1-H): verification record

**Branch:** `v1.4.23.1-H/invoice-number-uniqueness` · **Package version:** `1.4.37`
**Migration:** `supabase/migrations/0032_invoice_number_unique.sql` — applied to **test and production**.

## The problem

A `(user_id, invoice_number)` unique index couldn't be added because production
had **8 duplicate groups** (from the pre-v1.4.23-H duplicate-number generator bug;
see `development/invoice-number-duplicates-audit.md`).

## What the migration does

1. **Renames the later copy** in each group to `<first 20 chars> (dup N)`, keeping
   the earliest row's number as-is. Generic + idempotent (works on any DB).
2. Adds the unique index `invoices_user_id_invoice_number_idx` on
   `(user_id, invoice_number)`, **partial** on non-blank numbers — drafts can share
   a blank number, so they are exempt.

## Decision: rename, not delete

The plan allowed deletion (all rows are test data). Two reasons I renamed instead:

1. **Deletion is blocked for non-draft invoices** — the v1.4.21-H (S4) money-safety
   trigger `block_non_draft_delete` refuses it, and **6 of the 8 groups involve a
   non-draft row** (paid/pending/archived). Enforcing that trigger is the point of
   it.
2. Renaming is **reversible** and keeps the rows for the audit trail.

So nothing was deleted, and every row survives with a distinct number.

## The "export of the rows" — what that means, and why I skipped the file

An "export" just means **dumping the current rows to a file (CSV/JSON) before a
destructive change**, so you can restore or audit them if the change goes wrong.
It is *not* a Supabase feature — it's the same as "Save As" on a spreadsheet, or
a database backup of just those rows.

I judged a separate export file unnecessary here because the change is a
**rename, not a delete**: no row is removed, so there is nothing to restore. And
the full before-state *is* recorded — captured from production before the change
and reproduced here:
