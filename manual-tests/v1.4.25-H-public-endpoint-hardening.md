## What this changes

- **H-SEC-1** — the public PDF route now checks the access code (it was wide open).
- The access cookie's scope is widened to `/` (was `/invoice/<id>`), and it gains
  `secure` in production.
- **M-FE-6** — line items are capped at 100; the PDF is cached by version (ETag/304).
- The `btc-price` endpoint only accepts USD (400 otherwise).
- The cron secret is compared in constant time.

## Found bug (worth calling out)

The same cookie-scope problem was already breaking a live path. The payer's
fast-detection route (`/api/invoices/[id]/payment-status`) reads that cookie and
returns 404 without it. Because the cookie was scoped to `/invoice/<id>`, it was
never sent to `/api/...`, so **for any access-protected invoice the payer's live
fast-path detection failed silently** and those invoices only advanced via the
5-minute sweep. The e2e test never caught it because that invoice had no access
code. Widening the cookie to `/` fixes it. This is a bug fix, not just a
supporting change.

### 3b. The fast-path bug, isolated (curl)

A `400` alone does not prove the cookie reached the gate, because the route checks
the request body before the access gate. So this uses a well-formed 64-hex txid
and inspects the error message, which only exists past the gate:

```
with cookie    -> HTTP 400  {"error":"Transaction does not pay to invoice address"}
without cookie -> HTTP 404  {"error":"Invoice not found"}
```

The first message is only reachable after the access check passes, so the cookie
reached the fast-path. Before this branch both returned `404`.

### 4. Constant-time secret compare

`src/lib/timing-safe.test.ts` covers equal / unequal / unequal-length / null
cases. The cron route and the access-code check both use it.

### 5. Line-item cap

`actions.test.ts` asserts a 101-item invoice is rejected on create, and that
duplicating a source with 101 items is also refused. The cap is 100, enforced on
create, update, and duplicate.
