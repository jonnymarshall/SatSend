# v1.4.23-H — RLS & indexes: manual tests

**Branch:** `v1.4.23-H/rls-and-indexes`
**Migration:** `0029_rls_and_indexes.sql`

## What this changes

- `pre_archive_status`: `text` → the `invoice_status` enum (+ a CHECK forbidding
  `draft`/`archived`), so un-archiving can no longer write a stale value.
- `invoice_email_summary` recreated with its columns enumerated (no `select i.*`),
  with `security_invoker` and the anon revoke re-asserted.
- `invoices (user_id, created_at desc)` index, and `auth.uid()` wrapped as
  `(select auth.uid())` in all three RLS policies.
- `email_events.updated_at` is now maintained by a trigger, not by the webhook code.
- Webhook dedupe: only Postgres `23505` counts as a duplicate (any other insert
  error is a 500, not a silent 200), the claim is released if a later step fails
  so Svix can retry, and deliveries older than 30 days are swept.
- Un-archive now reports a legacy row it cannot restore instead of guessing.
- Duplicate-invoice numbers are now unique (` (copy)`, ` (copy 2)`, …).

> **Not in this migration:** the `(user_id, invoice_number)` unique index.
> Production already has duplicates; see
> `development/invoice-number-duplicates-audit.md`. The generator that created
> them is fixed here.

## Setup

```bash
set -a; source .env.local; set +a
sb() { curl -s "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/$1" -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY"; }
```

Run the migration on production first (via `supabase-migrate`). All SQL below is
run against the **test** project in the Supabase SQL editor unless noted.

---

### TEST 1 — migration applied (SQL)

**Proves:** the enum, index, view hardening and trigger all landed.

**Run:**
```sql
select
  (select udt_name from information_schema.columns
     where table_name='invoices' and column_name='pre_archive_status') as pre_archive_udt,
  (select indexname from pg_indexes
     where tablename='invoices' and indexname='invoices_user_id_created_at_idx') as user_id_index,
  (select array_to_string(reloptions,',') from pg_class
     where oid='public.invoice_email_summary'::regclass) as view_reloptions,
  (select tgname from pg_trigger
     where tgrelid='public.email_events'::regclass and not tgisinternal) as trigger;
```

**Expect:** `pre_archive_udt = invoice_status`, `user_id_index = invoices_user_id_created_at_idx`,
`view_reloptions = security_invoker=on`, `trigger = email_events_set_updated_at`.

---

### TEST 2 — anon cannot read the view (SQL)

**Proves:** the recreate did not reopen the S1 CRIT-1 exposure.

**Run:**
```sql
select array_agg(distinct grantee) from information_schema.role_table_grants
 where table_name='invoice_email_summary';
```

**Expect:** `{authenticated,postgres,service_role}` — **no `anon`**.

---

### TEST 3 — un-archive skips a row with no recorded status (UI)

**Proves:** a legacy archived row is left alone and reported, not downgraded to pending.

**Setup:** find or make an archived invoice whose `pre_archive_status` is null:
```sql
select id from public.invoices where status='archived' and pre_archive_status is null limit 1;
```
If none exists, archive a normal invoice, then `sb "invoices?id=eq.<id>"` PATCH
`{"pre_archive_status":null}` (service role bypasses the CHECK because it sets null).

**Run:** open `/invoices/<id>` and click **Unarchive**.

**Expect:** a red notice: *"…can't be unarchived automatically because its previous
status wasn't recorded…"*, and the row is **still archived** in the DB. (A row with
a recorded status unarchives normally.)

---

### TEST 4 — duplicate invoice numbers are unique (UI)

**Proves:** the generator fix.

**Run:** open an invoice, click **Duplicate**, then duplicate the **copy** it created.

**Expect:** the first copy is `<number> (copy)`, the second is `<number> (copy 2)`
(never the same string twice).

---

### TEST 5 — Resend webhook replay (HTTP)

**Proves:** a genuine duplicate is ignored, not reprocessed.

**Run:** send the same Resend event twice (Resend dashboard "resend", or replay the
same `svix-id`), and watch the HTTP status.

**Expect:** both return `HTTP 200`, the second with `{"ok":true,"dedupe":"duplicate"}`,
and no second `email_events` update. (The "insert error that is not 23505 → 500 +
claim released" path is covered by unit tests; it needs a DB fault to reproduce.)

---

### TEST 6 — a signed-in owner can still read the view (UI)

**Proves:** `security_invoker` + the re-grant keep the dashboard working.

**Run:** sign in and open `/invoices` (it reads `invoice_email_summary`).

**Expect:** the list renders as before, no empty/error state.
