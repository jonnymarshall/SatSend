# v1.4.26.1-H — Rate limiting (done): verification record

**Decision date:** 2026-10-08 · **No repo changes** (the rule lives in Vercel).

## Rate limiting — done via Vercel Firewall (free, Hobby)

| Setting | Value |
|---|---|
| Rule name | `rate-limit-public-invoice-routes` |
| Conditions (OR) | path starts with `/invoice/`, `/api/invoice/`, `/api/invoices/` |
| Action | Rate Limit — fixed window, 60 s, **30 requests**, key **IP** |
| Fallback | default 429 |

Those three prefixes are the abuse surface: the access-code gate posts to
`/invoice/<id>`; the public PDF and payment polling live under the two API
prefixes. The dashboard is `/invoices` (with an `s`), which `/invoice/` does not
match, so the owner cannot lock themselves out. 30/min/IP is far above any
legitimate payer and makes online guessing of codes pointless. Hobby allows exactly
one rate-limit rule, and this uses it — so **do not build an app-level limiter**.

**Rate limiting is configured in Vercel, not in git.** If it ever needs to change,
it is a Vercel dashboard edit; the **`deploy-checklist`** skill lists it as a
pre-promote check.

## Hashed access codes — scrapped (not built)

Considered storing a keyed hash (HMAC) of the access code instead of plaintext.
**Rejected:** the cost outweighed the gain —
- owners could no longer see or resend their code (dashboard + published email both
  surface it today);
- the published email prints the code to the payer, which hashing breaks;
- with online guessing now rate-limited, the security gain is small.

Codes stay **plaintext** in `invoices.access_code`. The v2.3 client-page code
cascade is unaffected either way (it never reads invoice codes).
