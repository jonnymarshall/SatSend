# v1.4.31-H — Address uniqueness across tenants: verification record

**Branch:** `v1.4.31-H/address-uniqueness`
**Migration:** `0030_address_registered_rpc.sql` (applied to the test database; **apply to production after merge**).

## The bug (H-DB-3)

`addressUniquenessError` runs on the RLS-scoped client, so it only ever sees the
caller's own invoices, while the `btc_address` unique index is global. Reusing an
address another user holds therefore passed every app check and only failed at
the insert — as a raw Postgres error (softened to a field error by v1.4.29-H, but
still after the fact).

## What this changes

A `security definer` RPC `is_address_registered(addr)` answers "is this address on
any non-draft invoice?" across tenants, so the collision is caught at **validation
time**. The check is layered:

1. **Own-row lookup** (RLS-scoped) → the specific message that names *your* invoice.
2. **RPC** (cross-tenant) → a generic message (naming another tenant's invoice
   would leak more).
3. **`23505` catch** (v1.4.29-H) → covers the race between check and insert.

### Hardening (first security-definer function in the repo)

- `set search_path = ''` on the function (no search-path hijack), with the body
  fully schema-qualified (`public.invoices`).
- `revoke all … from public` + `grant execute … to authenticated` — signed-in
  users only, not the open internet.
- Mirrors existing semantics: **non-draft** invoices only.

## Honest scope

This does **not** close the cross-tenant oracle. A user who probes an address
still learns "this is registered on the platform", just via a clean field error
instead of a distinct database failure. That leak is intrinsic to global
uniqueness. The mitigation is rate limiting (already queued in **v1.4.26.1-H**).
What this buys is the real prize: the pre-check stops lying and the error arrives
at the right time.
