# v1.4.20-H (S1) — Close the Four Anon Database Exposures: Manual Test Guide

## What this version does

The 2026-07 master architecture audit found that the anon (public) API key could read far more than it should:

- **CRIT-1:** `invoice_email_summary` is a plain view (`select i.*` from `invoices`). Views run with the *owner's* privileges by default, not the caller's — so it bypassed RLS entirely and handed anon every invoice (draft or not), including `access_code` and `user_id`.
- **CRIT-2:** `webhook_deliveries` had no RLS at all — any anon request could read the whole dedupe table.
- **CRIT-3:** the `anon_select_non_draft` policy let anon read every non-draft invoice's full row via `postgres_changes` — far more than the payer page actually needed (just `status`/`btc_txid`).

This branch closes all three, and along the way also strips `access_code`/`user_id` out of the object the public `/invoice/[id]` page passes to its client component (so it never reaches the browser at all, even in the React payload), and marks `src/lib/supabase/admin.ts` `server-only`.

The payer page's live-update feature (previously `postgres_changes`) is replaced with a DB-triggered **broadcast**: a Postgres trigger on `invoices` calls `realtime.broadcast_changes()` on every non-draft UPDATE, sending only `{id, status, btc_txid}` to a channel named `invoice:<id>`. An RLS policy on `realtime.messages` (not `invoices`) authorizes anon to receive it.

## One-time setup

```bash
set -a; source .env; set +a
sb_service_select() { curl -s "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/$1" -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY"; }
sb_anon_select() { curl -s "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/$1" -H "apikey: $NEXT_PUBLIC_SUPABASE_ANON_KEY" -H "Authorization: Bearer $NEXT_PUBLIC_SUPABASE_ANON_KEY"; }
sb_update() { curl -s -X PATCH "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/$1" -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" -H "Content-Type: application/json" -H "Prefer: return=representation" -d "$2"; }
```

Restart the dev server after pulling this branch (`Ctrl-C`, then `npm run dev`) — the payer page's realtime hook changed and needs a fresh client bundle.

## The tests

### TEST 1 — Anon cannot read `invoice_email_summary` at all

**Proves:** CRIT-1 is closed — the view no longer bypasses RLS, and anon's grant on it is revoked outright.

**Run:**
```bash
sb_anon_select "invoice_email_summary?select=*" | jq
```

**Expect:** `{"code":"42501", ... "permission denied for view invoice_email_summary"}` (or similar permission-denied response) — not a list of invoices.

---

### TEST 2 — Anon cannot read `webhook_deliveries`

**Proves:** CRIT-2 is closed.

**Run:**
```bash
sb_anon_select "webhook_deliveries?select=*" | jq
```

**Expect:** `[]` (RLS enabled, zero policies — empty result, not an error, since PostgREST returns an empty set rather than a permission error when RLS silently filters every row).

---

### TEST 3 — Anon cannot read `invoices` directly anymore

**Proves:** CRIT-3's blanket policy is gone. Contrast with the old v1.4.2 test guide, which expected non-draft rows to come back for anon — that should no longer happen.

**Run:**
1. Create and publish a test invoice. Copy its ID: `INV_ID=<id>`.
2. ```bash
   sb_anon_select "invoices?id=eq.$INV_ID&select=id,status,access_code" | jq
   ```

**Expect:** `[]`. No row comes back for anon, published or not.

---

### TEST 4 — Payer page still live-updates via the new broadcast channel

**This is the core regression check.** Proves the payer page's live-update feature still works despite anon losing all table-level read access.

**Behind the scenes:** the page now subscribes to a *broadcast* channel `invoice:<id>` (not `postgres_changes`), opened with `{ config: { private: true } }`. A trigger on `invoices` sends `{id, status, btc_txid}` to that channel on every non-draft UPDATE; a policy on `realtime.messages` authorizes anon to receive it.

**Run:**
1. Create and publish a new testnet invoice. Copy its ID: `INV_ID=<id>`.
2. Open `/invoice/<id>` in a browser. Confirm the badge says **Pending**. Leave the tab open — do not refresh.
3. Open DevTools → Network → filter `WS`. Confirm a websocket connection to your Supabase project's realtime endpoint is open.
4. In the terminal:
   ```bash
   sb_update "invoices?id=eq.$INV_ID" '{"status":"payment_detected","btc_txid":"deadbeef"}' > /dev/null
   ```

**Expect:** within ~1 second, the badge flips to **Payment Detected** without any refresh, and the QR/address area auto-reveals.

5. Repeat with `paid`:
   ```bash
   sb_update "invoices?id=eq.$INV_ID" '{"status":"paid"}' > /dev/null
   ```

**Expect:** badge flips to **Paid** within ~1 second.

> If the badge doesn't move: open DevTools → Console for a `[public-invoice-realtime]` warning. `CHANNEL_ERROR` most likely means the `realtime.messages` RLS policy from migration `0023` didn't apply, or the client isn't opening the channel with `{config: {private: true}}`. Also confirm in the Network → WS frames that a `broadcast` message actually arrived — if a message arrives but the badge doesn't move, the bug is in payload parsing (`payload.payload.record`), not authorization.

### TEST 5 — Draft invoices never broadcast

**Proves:** the trigger's draft guard works — a draft invoice being edited doesn't leak a broadcast to anyone who might be listening on its channel (defense in depth; nobody has the URL for a draft anyway, but the trigger shouldn't fire regardless).

**Run:**
1. Create a new invoice, leave it as a **draft**. Copy its ID: `DRAFT_ID=<id>`.
2. In the terminal, force an update on it while it's still a draft (e.g. touch `updated_at` or any field via the service-role key):
   ```bash
   sb_update "invoices?id=eq.$DRAFT_ID" '{"invoice_number":"test-edit"}' > /dev/null
   ```
3. Check whether anything landed on that invoice's broadcast topic — easiest way is to open a throwaway browser console tab against your Supabase project and subscribe manually:
   ```js
   const { createClient } = supabase; // if testing from browser console with the JS SDK loaded
   ```
   (Simplest in practice: skip the manual subscribe and just confirm no error/exception occurred and the update succeeded — the trigger function returns early for `status = 'draft'` before calling `broadcast_changes`, so there's nothing to observe on the wire either way. This test is really a code-reading confirmation: open `supabase/migrations/0023_broadcast_guard_and_authorization.sql` and confirm the `if new.status = 'draft' then return null; end if;` guard is present.)

**Expect:** the guard clause is present in the trigger function; the update to the draft succeeds normally (the guard only skips the broadcast, not the write).

### TEST 6 — `access_code` and `user_id` never reach the payer's browser

**Proves:** even though the RLS fixes make table reads impossible for anon, this test proves the *page's own* server-rendered payload (the RSC prop tree, not a Supabase query) was also cleaned up — the fix in `src/lib/invoice-public.ts` (`toPublicInvoice`).

**Run:**
1. Open `/invoice/<id>` for any published invoice with an access code set.
2. View page source (`Cmd+Option+U` / `Ctrl+U`) or inspect the Next.js RSC payload in DevTools → Network → the document request's response body.
3. Search (`Ctrl+F` in the page source) for the invoice's actual access code value, and for `access_code` / `user_id` as field names.

**Expect:** no match. The access code value should not appear anywhere in the HTML or embedded RSC payload, and neither should the `user_id` field name with a value.
