# v1.4.31.2-H — Integration harness, second suite (DB invariants): verification record

**Branch:** `v1.4.31.2-H/db-invariants`
**Run:** `npm run test:db` (or `node test-automation/db-invariants.mjs`)
**Migrations:** none (exercises migration `0027`'s constraints and triggers).

## Why

The first suite (`v1.4.31.1-H`) proved the lesson: rules that live only in the
database are invisible to the mocked suites. The money and status invariants from
`0027` are exactly that — CHECK constraints and triggers. This suite proves they
actually fire against real Postgres.

## What it proves

- Impossible money is rejected (`23514`): total ≠ subtotal + tax, negative
  amounts, non-USD currency, tax percent > 100, malformed `line_items`, and a
  line item missing `unit_price`.
- A **non-draft invoice cannot be deleted** (the financial audit trail is safe).
- A **paid invoice's money is frozen**, but its **status stays writable** (the
  detection flow still needs to write it).
- A **draft can be deleted** (the one allowed case) — so the passing rejections
  above are meaningful, not an artefact of everything failing.

## Guardrails

Same as the first suite: test project only (aborts on a production URL),
aborts if `PAYMENT_SWEEP_ENABLED` is set, skips cleanly without an anon key,
secrets never printed. Creates one throwaway user + invoices, cleans up
(flip to draft → delete) and removes the user.
