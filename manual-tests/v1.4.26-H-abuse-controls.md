# v1.4.26-H — Abuse controls (code side): verification record

**Branch:** `v1.4.26-H/rate-limiting`
**No migration.**

This branch ships the code-side abuse controls only. Rate limiting and hashed
access codes are split to **v1.4.26.1-H** (see the roadmap).

## What this changes

- **Server-side client email validation.** Empty is fine, malformed is rejected, on
  save (create/update) and again at send time. A malformed address at send time
  skips quietly (publishes, does not attempt a send) rather than failing at the
  provider.
- **Minimum access-code length** of 6, enforced on save.
- **Per-user daily send cap of 200**, enforced in the shared send helper
  (`src/lib/email/send.ts`), counting `email_events` rows over a rolling 24h.
  - At the cap, **automated** sends (detected/confirmed) are skipped and the
    caller carries on. The helper never throws, so a capped send cannot crash the
    sweep or the payer fast-path mid-flight (the S3 failure mode).
  - **Owner-initiated** sends (publishing from the dashboard) surface a visible
    error.
  - A capped send inserts **no** row, so the count cannot inflate itself.

## Verification

### Automated (576 tests, was 567)

- `src/lib/email/send.test.ts`: at the cap the helper returns
  `skipped_daily_cap`, inserts nothing, and sends nothing; and a failing cap
  check does not block mail.
- `src/app/(dashboard)/invoices/actions.test.ts`: malformed `client_email`
  rejected on save, blank allowed; access codes under 6 rejected, 6 allowed;
  `publishAndSendEmail` skips quietly for a malformed address (publishes, no
  send) and surfaces `skipped_daily_cap`.

### Live

- The cap's count query was run against the test database: the test user has **6**
  sends in the last 24h (far below 200), so the query is valid and the window is
  right.
- App smoke after the change: `/api/btc-price?currency=USD` → 200, `/login` → 200.

### Honest gap

The save and send server actions are auth-gated, so their validation is covered by
unit tests rather than a live click-through; a full live send needs a logged-in
session (the test account cannot be handed a shareable login link — the app uses
PKCE magic links). The send-helper logic itself is fully unit-tested, including
the cap.

## Deferred to v1.4.26.1-H

- **Rate limiting** on the access-code check / email send / PDF route. Custom WAF
  rules are a Vercel **Pro+** feature; the project is on Hobby. Deferred rather
  than replaced with a DIY limiter: with the new 6-character minimum a code has
  ~2 billion combinations, guessed one HTTP round-trip at a time, which is not a
  practical attack.
- **Hashed access-code storage.** Needs a migration and two decisions first:
  owners currently *see* their code in the dashboard (hashing makes it reset-only),
  and the check is case-insensitive (hashing needs a normalisation rule).

## Cleanup

No data changes. No migration.
