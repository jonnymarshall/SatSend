# v1.4.29-H — Zod + typed action results: verification record

**Branch:** `refactor/zod-validation`
**No migration.** New dependency: `zod`.

## The bug this fixes (H-FE-3)

Server actions used to `throw new Error("field: message")` for validation
failures. Next **masks thrown server-action messages in production** (the real
text only appears in dev), so in production every field error collapsed to a
useless generic message — the form received the masked string via
`parseServerError` and showed nothing helpful. It worked perfectly in dev, which
is why it slipped through.

Field failures are now **returned**, not thrown: `{ ok: false, field, message }`,
which survives production.

## What this changes

- **Zod + one shared `invoiceSchema`** (`src/lib/invoices/schema.ts`) covering the
  rules the server enforced: invoice-number length, email format, access-code
  minimum length, line-item count, tax range.
- **Actions return typed results.** `saveDraft`, `updateDraft`, `publishInvoice`,
  `publishAndSendEmail`, `publishAndMarkSent`, and `duplicateInvoice` return
  `ActionResult<T>`. Structural errors ("Invoice not found", "Forbidden") still
  throw — those belong to error boundaries, not form fields.
- **DB constraint errors are translated** (`dbErrorToFieldError`): a unique
  violation on the address index (`23505`) becomes
  `{ field: "btc_address", message: "already in use" }`. This is the flagship
  case — the duplicate-address message came from the Supabase passthrough, not
  the hand-written checks, so without this the headline example would still be
  broken in production. (The invoice-number constraint is handled too, ready for
  v1.4.23.1-H.)
- **Callers consume results:** the form, the table, and the detail page check
  `result.ok` and show the field message; `parseServerError` is deleted.

## Deliberately not changed

- **Address FORMAT** is not added to the schema. The server-side save path never
  validated format (the form does, client-side, and publish validates via
  `canPublishInvoice`), so adding it would be new rejection behaviour outside this
  branch's scope.
- **The form's three parallel arrays** (M-FE-2) are untouched — that is the
  follow-up **v1.4.29.1-H**.

## Verification

- `npm run typecheck` — 0 errors.
- `npm run test:run` — 576 passed.
- `npm run lint` — 0 errors.
- Regression guard: `actions.test.ts` asserts the action **returns** the field
  error (not `rejects.toThrow`) for every validation path, including a DB
  `23505` on the address index → `{ ok: false, field: "btc_address" }`.

## What you'll observe

- When a save or publish fails validation, the user sees the **actual reason** in
  production ("This bitcoin address has already been used on invoice X"), not a
  generic "something went wrong". That is the point of the branch.
