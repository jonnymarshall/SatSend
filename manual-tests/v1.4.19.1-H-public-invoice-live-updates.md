# v1.4.19.1-H (S2.1) — Public invoice live updates: manual tests

**Branch:** `fix/public-invoice-realtime-authorization`
**Migration:** `0026_fix_invoice_realtime_policy.sql`

## What this fixes

The public payer page (`/invoice/[id]`) opens a private broadcast channel named
`invoice:<id>` and updates the status badge from it. Migration `0023` wrote the
`realtime.messages` permission rule against the `topic` **column**, but Supabase
checks the rule against the **requested** channel topic, which it exposes through
the `realtime.topic()` helper. The rule never matched, so every join was refused
(`Unauthorized: ... you do not have permissions to read from this Channel topic`)
and the page only updated on a refresh.

`0026` recreates the rule using `(select realtime.topic())` and widens it from
`to anon` to `to anon, authenticated` (an owner previewing their own public link
is signed in, so their socket counts as `authenticated`).

> **Main signal:** the browser console showing `subscribed` and no
> `CHANNEL_ERROR`.
>
> **If it still fails:** the remaining suspect is the Supabase Realtime "Allow
> public access" setting (Dashboard → Project Settings → Realtime) needing to be
> off. That is a settings switch, not a code change.

## Setup

Restart the dev server after pulling the branch.

In a terminal, load the env and define the helpers. `sb_update` prints the HTTP
status code **and** the response body, so you can cross-check the status against
the expected code.

```bash
set -a; source .env.local; set +a

sb_service_select() { curl -s "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/$1" -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY"; }

sb_update() {
  curl -s -o /tmp/sb_body.json -w 'HTTP %{http_code}\n' \
    -X PATCH "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/$1" \
    -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
    -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" \
    -H "Content-Type: application/json" \
    -H "Prefer: return=representation" \
    -d "$2"
  jq . < /tmp/sb_body.json
}

now_iso() { date -u +%Y-%m-%dT%H:%M:%SZ; }
```

Publish a testnet4 invoice and copy its ID.

```bash
INV_ID=<paste invoice id>
```

---

### TEST 1 — Public page subscribes (logged out)

**Proves:** the permission rule now matches, so the payer page can join its channel.

**Run:**
1. Open `http://localhost:3000/invoice/$INV_ID` in a private/incognito window (so you are logged out).
2. Open DevTools → Console.

**Expect:** a `[public-invoice-realtime] subscribed: invoice:<id>` line and no `CHANNEL_ERROR` line.

---

### TEST 2 — Live status change without a refresh (logged out)

**Proves:** the badge updates from the broadcast, not from a page reload.

**Run:**
1. Leave the page from TEST 1 open and untouched. In the terminal:
   ```bash
   sb_update "invoices?id=eq.$INV_ID" "{\"status\":\"payment_detected\",\"btc_txid\":\"deadbeef\",\"mempool_seen_at\":\"$(now_iso)\"}"
   ```

**Expect:** `HTTP 200`, then the updated row as JSON. The badge on the still-open page flips to **Payment Detected** within about one second, with no refresh, and the console logs `[public-invoice-realtime] broadcast received`.

---

### TEST 3 — A signed-in viewer also subscribes

**Proves:** the widened `to anon, authenticated` rule covers a logged-in viewer.

**Run:**
1. Open the same `http://localhost:3000/invoice/$INV_ID` in your normal browser window, where you are signed in.
2. DevTools → Console.

**Expect:** `subscribed` with no `CHANNEL_ERROR`, same as TEST 1. Before this fix this case failed, because a signed-in socket counts as `authenticated`.

---

### TEST 4 — Draft invoices never broadcast

**Proves:** the trigger's draft guard still holds after the policy change.

**Run:**
1. Create an invoice and leave it as a **draft**. Copy its ID.
   ```bash
   sb_update "invoices?id=eq.<DRAFT_ID>" '{"invoice_number":"draft-touch"}'
   ```

**Expect:** `HTTP 200` and the row updates. No broadcast is delivered for a draft. This is mainly a code-reading check: the `if new.status = 'draft' then return null; end if;` guard in `0023` is unchanged by `0026`.

---

### TEST 5 — Anonymous still cannot read invoices

**Proves:** `0026` did not reopen the S1 database-exposure fix.

**Run:**
```bash
curl -s -i "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/invoices?select=id,status" -H "apikey: $NEXT_PUBLIC_SUPABASE_ANON_KEY" | head -20
```

**Expect:** either HTTP `200` with an empty array `[]`, or a `401`/`403`. Any list of invoice rows would be a regression.

---

## Quick smoke test (a couple of minutes)

Run **TEST 1** and **TEST 2**. Those cover the actual fix: the page subscribes, and a status change arrives without a refresh.
