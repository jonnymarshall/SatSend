# v1.4.34 — Branch protection + v1.4.36 close-out: verification record

**Branch:** `chore/branch-protection`. Config/docs + one script; no app code.

## Why

`main` had no protection, so the CI added in v1.4.33-H could be bypassed — by a
direct push to `main`, or by merging without the check. Branch protection is the
piece that makes CI actually bite.

## What

- **`scripts/enable-branch-protection.sh`** — idempotent `gh api` call that
  requires the CI `verify` check, requires PRs to be up to date, and blocks
  direct pushes / force-pushes / deletion on `main` (`enforce_admins = true`, so
  it applies to the owner too; a comment shows how to relax it for emergencies).
- `AGENTS.md` project brief notes that `main` is protected.
- `development/OUTSTANDING-VERIFICATIONS.md` gains the branch-protection status
  and the leftover testnet-wallet sweep.
- `development/ROADMAP.md`: v1.4.36 closed (its only remainder is the on-chain
  sweep, now tracked).

## Manual test (owner)

```bash
# Enable (needs admin):
bash scripts/enable-branch-protection.sh
# Verify:
gh api repos/jonnymarshall/SatSend/branches/main/protection --jq '.required_status_checks.contexts'
#   -> ["verify"]

# Prove it blocks: from a clone, try a direct push to main.
git checkout main && git commit --allow-empty -m "test" && git push origin main
#   -> rejected: "protected branch"
```

UI alternative: Settings → Branches → Add branch protection rule → branch name
`main` → tick "Require status checks to pass before merging" → select `verify`
→ tick "Require branches to be up to date" → tick "Do not allow bypassing the
above settings" → Save.
