# v1.4.36 — One colour source of truth (roadmap v1.4.30.1-H): verification record

**Branch:** `v1.4.30.1-H/colour-source` · **Package version:** `1.4.36`

## The drift

`globals.css` `.dark` tokens render to one set of colours; `brand-colors.ts` (used
only by the PDF, `invoice-pdf.tsx`) held a different set — the hexes the CSS
*comment* claimed, not the hexes the OKLCH actually produces:

| Token | CSS OKLCH | Browser hex | was in brand-colors.ts |
|---|---|---|---|
| `--background` | `oklch(0.06 0 0)` | `#010101` | `#0A0A0A` |
| `--card` | `oklch(0.13 0 0)` | `#070707` | `#181818` |
| `--primary` | `oklch(0.56 0.2 22)` | `#D02A3A` | `#DE3C4B` |
| `--muted-foreground` | `oklch(0.55 0.03 112)` | `#727460` | `#7C7F65` |

So the PDF's accent and muted text did not match the app.

## Decision — `globals.css` is canonical

The app is what users see; the tokens are what it actually renders. Two reasons:

1. The roadmap defers visual styling to the v1.5 redesign, so **this change must
   not alter how the app looks.** Making the CSS canonical changes nothing on
   screen; the alternative (treating the declared hexes as the brand) would mean
   re-tinting the dark UI now — a v1.5 job.
2. The PDF/email should mirror the app.

Consequence: `brand-colors.ts` now carries the browser-accurate hex of the tokens,
and its comment no longer contradicts the CSS.

## The guard

`src/lib/brand-colors.test.ts` reads the `.dark` block, converts each OKLCH token
to sRGB with the CSS Color-4 algorithm, and asserts the matching `brandColors`
field is within **±2 per channel** (tolerance for rounding). `foreground` and
`paper` are PDF-only (no `.dark` token) and are not guarded.
